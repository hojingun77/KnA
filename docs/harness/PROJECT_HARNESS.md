## 1. 프로젝트 개요

- **서비스:** 한국에 거주하는 외국인이 생활·행정 정보를 질문하고 답변을 얻는 K&A Q&A 앱.
- **현재 코드:** React 19, Vite 8, JavaScript/JSX, Tailwind CSS 3, React Router 7, Zustand 5, i18next(한국어·영어·베트남어·중국어 사전). Firebase Web SDK와 Algolia 의존성 및 초기화 모듈은 있지만 실제 인증·데이터 기능에서 사용되는 상태는 아니다.
- **현재 진행 상태와 목표:** IndexedDB·데모 로그인·홈·질문·포인트 1차 구현을 진행 중이다. 로컬 Node API를 경유해 질문 등록 시 검색 없는 LLM 보상 등급 분류, 답변 등록 후 짧은 웹 검색 기반 사실 비교를 추가할 계획이다. 이 API와 두 LLM 기능은 아직 구현되지 않았다. 클라우드 배포, Firebase Emulator, Supabase 또는 SQL 데이터 API는 아직 선택하거나 연결하지 않는다. 서버 동기화는 나중에 붙일 수 있도록 데이터 접근 경계와 식별자를 정돈하되, 동기화 엔진·충돌 해결은 미리 만들지 않는다.
- **주요 경로:** `src/pages`, `src/components`, `src/api`, `src/store`, `src/constants`, `src/i18n`.
- **개발 방식:** 1인 개발을 전제로 작고 검토하기 쉬운 변경을 우선한다. 팀 규모를 위한 분리 구조나 복잡한 아키텍처를 미리 도입하지 않는다.
- **저장소 상태 참고:** 초안 작성 시 `main`이 `origin/main`을 추적하고 작업 트리는 깨끗했다. 브랜치와 작업 트리는 작업마다 다시 확인한다.

## 3. 설계 원칙

1. React 컴포넌트는 표시와 사용자 입력을 맡고, 계정·프로필·질문·답변·설정·포인트 데이터는 기능별 비동기 저장소 모듈을 통해 읽고 쓴다. 첫 구현 대상으로 브라우저 IndexedDB를 선택했으며 아직 저장소 구현은 시작 전이다. 화면은 저장소 구현 세부사항을 직접 알지 않도록 설계한다.
2. IndexedDB를 로컬 프로토타입의 데이터 원본으로 사용한다. Zustand는 화면 상태와 현재 데모 세션에만 사용하고, 사용자 콘텐츠와 포인트 원장을 Zustand persist나 `localStorage`에 복제하지 않는다.
3. 시연용 사용자는 가짜 계정 데이터로 준비한다. 로컬 데모 로그인은 UI 흐름일 뿐 실제 인증·보안 경계가 아니며, 비밀번호를 사용자 프로필·IndexedDB·로그에 저장하지 않는다. 공개 시연 전에 사용할 자격 증명은 테스트 전용이며 번들에서 확인할 수 있음을 전제로 한다.
4. 동기화를 염두에 둔 데이터에는 안정적인 ID, `ownerId`, UTC 기준 생성·수정 시각을 둔다. 삭제 동기화가 필요해지기 전에는 실제 삭제를 허용하되, 서버 연동 단계에서 tombstone·버전·충돌 정책을 확정한다. 지금 동기화 큐나 충돌 해결기를 구현하지 않는다.
5. 포인트 데모 데이터는 포인트 원장과 과거 표시용 스냅샷을 구분한다. 1P=1원이며, 질문자 `skyking`과 답변자 `cutetl123`은 각각 1,000P로 시작한다. 답변자의 과거 내역·월간 요약은 7.5절의 시연 스냅샷으로 보관하고 시작 잔액에 다시 더하거나 빼지 않는다. 새 전환 시도는 안내 토스트만 표시하며 잔액·원장·내역을 변경하지 않는다. 실제 상품권 발급이나 서버 처리가 완료된 것으로 표현하지 않는다.
6. 현재 구현과 목표 설계를 문서·주석·응답에서 구별한다. 아직 없는 서버 API, Firebase Rules, Functions, 외부 업로드 또는 동기화를 구현된 것처럼 표현하지 않는다.
7. K&A는 로그인 사용자 전용 서비스다. 로컬 프로토타입에서는 준비된 두 데모 계정으로만 로그인하고, 가입으로 추가 계정을 생성하는 흐름은 첫 시연 범위에서 제외한다. 로그인 전에는 로그인·정책 안내만 허용하고 사용자별 질문·답변·첨부·설정 데이터를 세션에 따라 구분한다. 이는 UI 동작이며 보안 보장은 아니다.
8. Firebase나 다른 클라우드 저장소로 자동 연결하지 않는다. 현재 허용할 외부 연동 범위는 검색 없는 질문 보상 등급 분류용 LLM과 제한된 답변 평가용 LLM·웹 검색이며, 해당 기능을 구현한 뒤 명시적으로 활성화한 모드에서만 호출한다. 번역·검색 인덱스·상품권·배포 등으로 이 범위를 자동 확장하지 않는다. 하네스 활성화·개발 설정 단계에서는 본문 전송이나 유료 호출을 하지 않는다.
9. UI 문구는 i18next 언어별 사전에 둔다. 로그아웃 상태와 로그인 화면은 브라우저가 제공하는 기본 언어(`navigator.language`)를 사용한다: `ko-*`는 한국어(`ko`), `en-*`는 영어(`en`), `vi-*`는 베트남어(`vi`), `zh-*`는 중국어 간체(`zh-CN`)로 정규화하고, 그 외 언어는 영어로 대체한다. 로그인 후에는 계정의 지원되는 `uiLanguage`를 우선한다. 값이 없거나 지원하지 않으면 감지한 브라우저 언어를 쓰며, 로그아웃하면 브라우저 언어로 돌아간다. 질문·답변 등 가변 사용자 콘텐츠의 Google Translation + sLLM 번역은 별도 기능 도입 단계의 방향으로 보관한다. 도입 시 사용자가 실행한 원문만 번역하고 원문을 덮어쓰지 않으며, 이번 두 LLM 기능의 구현 범위에 번역 호출을 자동 추가하지 않는다. 고정 UI 문구를 화면을 열 때마다 번역 API로 생성하지 않는다.
10. 답변 평가는 UI·저장소에서 분리된 provider 계약과 로컬 Node 서버 adapter로 설계한다. 기본 목표는 질문 제목·본문·답변 본문을 외부 LLM에 전달하고 짧은 웹 검색 근거와 비교하는 `llm` provider다. [평가 룰](./ANSWER_EVALUATION_RULES.md)에 따라 핵심 사실별 판정을 평균해 0.0~100.0의 참고 점수·이유·출처를 질문자에게 표시한다. 문체 등 품질 평가는 제외한다. 근거 부족·검색 실패에는 점수 없이 상태를 표시하고 난수로 대체하지 않는다. 자체 RAG 자료 수집·Vector DB·Deep Research는 만들지 않는다. 프롬프트 기반 첫 구현과 실제 모델 가중치 파인튜닝은 구분하며, 현재 학습 완료된 모델이 있다고 가정하지 않는다.
11. 질문 보상은 [포인트 책정 룰](./QUESTION_REWARD_RULES.md)에 따라 질문 제목·본문만으로 제한된 등급을 분류한다. 모델에는 금액·가산율·지급 권한을 맡기지 않고, 앱이 허용 등급을 금액에 매핑하고 긴급 50%를 가산한다. 답변 평가와 요청·출력·정책 버전을 분리하며, 질문 등록 시 확정한 보상 스냅샷을 채택 때 그대로 사용한다.

## 4. 향후 서버 연동 보안 기준 (백엔드 미확정)

이 절의 Firebase·실서비스 권한 항목은 향후 데이터 서버를 연결할 때의 기준이다. 프로토타입의 데이터는 브라우저 IndexedDB에 저장하고 서버 보안이 적용된 것으로 간주하지 않는다. 아래 Firebase 세부사항은 Firebase를 백엔드로 선택할 때만 적용한다. SQL 계열을 선택하면 동일한 권한 원칙을 PostgreSQL RLS와 서버/API 검증에 맞춰 다시 설계한다. 데이터 클라우드는 연결하지 않으며, 현재 범위의 외부 LLM 호출 경계는 4.7절을 따른다.

### 4.0 로컬 데이터 경계

- 사용자·질문·답변·설정·차단·포인트 시연 데이터는 IndexedDB에 저장한다. `localStorage`는 민감한 정보나 전체 사용자 데이터를 저장하는 용도로 사용하지 않는다.
- IndexedDB는 현재 브라우저 프로필에만 존재한다. 다른 PC와 공유·동기화되지 않으며, 브라우저 데이터 초기화 시 사라질 수 있음을 시연 환경에서 고려한다.
- 데모 로그인은 아래 2개 시드 계정의 이메일과 비밀번호를 완전히 일치 비교한 뒤 해당 로컬 사용자로 UI 세션을 전환한다. 이메일 자동 보정·유사 문자열 허용·공백 제거·대소문자 무시를 하지 않고, 비밀번호도 대소문자를 포함해 정확히 비교한다. 한 글자라도 다르면 로그인을 거부한다. 이 로컬 검증은 데모 목적이며 실제 계정 보안이나 서버 인증을 제공하지 않는다.
- 초기 시드 데이터와 초기화 방법을 제공해 시연을 반복할 수 있게 한다. 질문자와 답변자 각각에 시작 원장 +1,000P를 한 번 생성하며 답변자의 과거 표시 내역·월간 요약도 7.5절에 따라 준비한다. 스냅샷 내역은 시작 원장에 재적용하지 않는다. 시드는 멱등적으로 만들고 재로그인·새로고침 때 시작 잔액으로 덮어쓰거나 추가 지급하지 않는다. 명시적인 데모 초기화 때만 계정별 시작 잔액과 과거 스냅샷을 함께 복원한다.
- 미래 동기화를 위해 저장소 인터페이스는 비동기로 정의하고, 화면은 IndexedDB API에 직접 의존하지 않는다. 서버 어댑터 교체 전까지 온라인 동기화·재시도 큐·다중 기기 충돌 처리는 범위에 넣지 않는다.

### 4.1 Firebase를 선택할 때: 인증과 권한

다음 규칙은 Firebase를 백엔드로 선택한 뒤에만 적용한다. 현재 로컬 데모 로그인에는 Firebase Auth를 사용하지 않는다.

- 질문·답변·첨부·검색을 포함한 서비스 데이터는 전부 Firebase Auth 인증을 요구한다. 비로그인 사용자는 가입·로그인·정책 안내 화면만 접근할 수 있다.
- 사용자 소유권은 `request.auth.uid`와 데이터의 소유자 UID를 비교해 확인한다.
- 역할·관리자 권한은 클라이언트가 수정할 수 있는 프로필 필드에서 읽지 않는다. 필요한 경우 신뢰된 Admin SDK 환경에서만 부여하는 custom claims 등으로 결정한다.
- 사용자 ID를 요청 본문에서 받더라도 인증된 UID와 일치하는지 검증한다. 클라이언트가 보낸 포인트, 역할, 작성자 표시 이름, 채택 보상액을 권한 근거로 쓰지 않는다.
- Firestore 규칙은 필터가 아니다. 쿼리는 허용 조건을 만족하도록 설계하고, 클라이언트 쿼리가 규칙상 가능한 문서 범위를 명확히 제한하도록 한다.

### 4.2 Firebase를 선택할 때: Firestore 접근 정책

다음 컬렉션·Rules 원칙은 Firebase 백엔드 선택 이후의 참고다. 현재 저장소나 IndexedDB에 Firestore 경로를 강제하지 않는다.

실제 컬렉션 경로와 공개 범위는 데이터 모델을 정한 뒤 아래 원칙에 맞춰 명시한다.

| 데이터/동작 | 기본 보안 원칙 |
|---|---|
| 사용자 개인·공개 프로필 | 개인 설정 문서는 본인 UID만 읽기·수정하고, 역할·포인트·제재 상태 등 서버 전용 필드는 클라이언트 수정 금지. 닉네임·아바타·언어/국가만 별도 공개 프로필로 분리하고 인증 사용자에게만 노출한다. |
| 질문·답변 읽기 | 인증 사용자만 읽기. 앱 내 모든 인증 사용자가 게시글을 볼 수 있으며, 비로그인 공개 읽기는 허용하지 않는다. 삭제된 질문과 차단된 질문은 사용자 화면과 검색 결과에서 제외한다. |
| 질문 생성 | 인증 사용자만 생성. 작성자 UID는 인증 UID와 일치해야 하며 필드 목록·자료형·문자 길이를 규칙에서 검증. 서버가 정하는 상태·점수·보상 필드는 클라이언트 생성 금지 또는 서버 검증. |
| 질문 수정·삭제 | 작성자는 본인 질문을 언제든 수정·삭제할 수 있다. 수정은 본문 등 편집 필드로 제한하고 소유자 UID·생성 시각·채택·지급 필드는 보호한다. 삭제는 사용자에게 즉시 비노출하는 논리 삭제로 처리하고 첨부 파일은 삭제한다. 포인트 원장과 최소 채택 이력은 수정·삭제하지 않는다. |
| 답변 생성·수정·삭제 | 인증 사용자만 생성. 작성자는 본인 답변을 언제든 수정할 수 있고, 채택되지 않은 답변은 삭제할 수 있다. 채택된 답변은 삭제할 수 없지만 내용 수정은 허용한다. 채택·지급 기록은 답변 수정으로 바뀌지 않는다. |
| 채택·포인트 원장·상품권 전환 | 클라이언트 직접 쓰기 금지. 신뢰 서버에서 질문자 권한·잔액·중복 요청을 검증하고 원자 처리한다. 질문자 수동 채택을 우선 권장하고, 7일 동안 미채택이면 7.2절의 유효 평가 후보 중 최고 참고 점수 답변을 자동 채택하는 보완 규칙을 둔다. 한 질문은 답변 하나만 한 번 채택할 수 있고 채택 취소는 지원하지 않는다. |
| 신고·차단·URL 공유 | 신고 및 개인별 차단은 인증 사용자 범위로 설계한다. 로컬 프로토타입의 신고·차단·공유는 목업 동작이며 운영자 계정·관리자 화면·실제 URL 공유는 만들지 않는다. |

- 기본은 명시적 허용이며, 마지막에 전체 경로를 열어 주는 포괄 규칙을 두지 않는다. 겹치는 규칙은 허용 조건이 합쳐질 수 있으므로 wildcard 규칙을 검토한다.
- 생성·수정 시 허용 필드 목록, 값의 자료형, 필수 여부, 길이/범위를 검증한다. 수정은 변경된 키 목록으로 보호 필드의 변경을 차단한다.
- 문서 경로만 믿지 말고 문서 데이터의 소유자 UID도 확인한다.
- Firestore Rules는 Admin SDK 권한을 제한하지 않는다. Cloud Functions 등 서버 측 쓰기 코드도 매 호출에서 인증, 권한, 입력, 중복·재시도 안전성을 검증한다.

다음은 필드 허용 목록을 제한하는 **규칙 본문 조각**이다. 독립 실행 가능한 규칙 파일이 아니며 `match` 블록 안에 들어갈 형태만 보여 준다. `displayName`, `languageCode`는 설명을 위한 후보 필드다. 운영 규칙을 만들 때는 스키마에 맞춰 생성·읽기·수정·삭제 권한 전체를 정의하고, 이 조각만 복사해 배포하지 않는다.

```javascript
function signedIn() {
  return request.auth != null;
}

function owns(uid) {
  return signedIn() && request.auth.uid == uid;
}

// match /users/{uid} 내부의 예시 패턴
allow update: if owns(uid)
  && request.resource.data.diff(resource.data).affectedKeys()
       .hasOnly(['displayName', 'languageCode']);
```

### 4.3 Firebase를 선택할 때: Cloud Storage 접근 정책

현재 로컬 프로토타입은 Cloud Storage를 호출하지 않는다. 아래 Rules와 서버 검사 기준은 Firebase Storage를 선택한 경우에만 적용한다.

- 파일 경로는 질문 ID 및 첨부 ID로 범위를 제한한다. 업로드·읽기·삭제 권한을 각각 정의하고, 업로드 작성자 UID와 부모 질문의 작성자·상태를 확인한다.
- 질문 첨부는 이미지 전용으로 시작한다: JPEG, PNG, WebP만 허용하며 질문당 최대 20개, 파일당 10 MiB, 질문당 총 50 MiB다. SVG, PDF, 동영상, 압축파일, 실행 파일, HEIC는 허용하지 않는다. HEIC 미지원은 업로드 전 안내한다.
- 수량·크기·MIME 형식은 UI뿐 아니라 Storage Rules와 서버 메타데이터 검사에서도 제한한다. 확장자나 클라이언트 MIME 값만 신뢰하지 않는다.
- 파일 이름이나 확장자만을 신뢰하지 않는다. 실제 서비스에서 민감한 업로드는 서버 측 검사와 악성 콘텐츠 대응 필요성을 평가한다.
- 첨부 읽기는 인증된 사용자에게만 허용하고, 해당 질문의 삭제·접근 상태와 사용자별 차단 여부를 UI에서 함께 확인한다. 원본 다운로드 URL을 공개 게시글이나 검색 인덱스에 넣지 않는다. Firebase 선택 시 인증 전용 열람은 규칙 적용 읽기(`getBlob`/`getBytes`)를 우선 검토하고, 장기 bearer URL의 외부 유출을 피한다.
- 로컬 프로토타입의 첨부 파일은 브라우저 IndexedDB 또는 저장소 안의 가짜 샘플 자산만 사용한다. 클라우드 업로드·공개 URL 발급은 구현하지 않는다.
- 기준을 정할 때 확인한 비교 자료에는 네이버 지식iN 사진 최대 50장/100MB, 네이버 블로그 파일 최대 20개/200MB·일반 파일 10MB, DC인사이드의 2020년 공지상 이미지 20MB/최대 50장이 있다. 공지 시점과 기능이 달라 시장 평균으로 사용하지 않는다. 첨부 개수는 2026-11-02 사용자 요청에 따라 20개로 변경했고, 개별 10 MiB·합계 50 MiB 및 허용 형식은 기존 기준을 유지한다.

### 4.4 향후 신뢰 서버, 포인트, 외부 서비스

현재 단계에서는 아래 Functions·App Check·Algolia·실서비스 거래 기준을 구현하지 않는다. 이는 데이터 서버 선택 이후의 참고 기준이다. 제한된 질문 보상 등급 분류와 답변 평가용 외부 AI는 4.7절 및 각각의 부속 룰에 따라 현재 개발 범위에 포함한다.

- 실서비스에서 포인트 잔액 변경, 원장 생성, 채택 확정, 상품권 전환, 관리자 작업은 브라우저의 클라이언트 쓰기로 수행하지 않는다. 로컬 프로토타입은 별도 로컬 저장소 어댑터가 시연 데이터를 갱신하며, 이를 서버 권한이나 실제 지급으로 기록하지 않는다.
- 수동 채택 확인 모달 문구는 Figma의 `이 답변을 채택할까요?`로 하고, 모달의 `채택하기`에서만 서버에 확정 요청을 보낸다. `취소`는 모달만 닫고 채택·포인트 상태를 바꾸지 않는다. 7일 미채택 시에는 서버가 최고 참고 점수 답변을 자동 채택하는 보완 흐름을 처리한다. 서버는 질문 상태·기한·답변과 질문의 관계·현재 revision의 완료된 평가 및 중복 여부를 확인해 수동 또는 자동 채택을 한 번만 확정한다. 동점은 먼저 작성된 답변, 작성 시각도 같으면 답변 ID 오름차순으로 결정한다. 유효 평가 후보가 없으면 보류한다. 확정 뒤 취소는 없다. 현재 로컬 시연의 실행 시점과 후보 제한은 7.2절을 따른다.
- 실서비스 포인트 지급은 답변 채택 성공 시 서버에서 한 번만 발생한다. 실서비스 원장은 append-only이며 잔액 캐시는 원장과 일치시킨다. 일반 편집·삭제는 지급을 되돌리지 않는다. 잘못된 중복 지급은 기존 원장을 지우지 않고 사유가 기록된 보정 원장으로 처리한다. 로컬 프로토타입도 시연 흐름을 위해 목업 원장 항목을 추가한다.
- 온누리 전환 프로토타입은 1P=1원으로 금액을 표시하고, 7.5절의 직접 입력 검증을 통과한 뒤 전환 버튼을 누르면 `디지털 온누리 서비스로 이동하여 계속해주세요.` 토스트만 잠시 표시한다. 잔액 차감·포인트 원장 추가·전환 내역 저장과 실제 앱 설치 확인·앱 연동·상품권 발급은 수행하지 않는다. 실제 전환은 공식 파트너 연동과 발급 성공 확인이 확보된 뒤 제공한다. 운영 최소액·단위는 해당 제휴/발급 계약으로 확정하며, 소비자 앱 충전 조건을 그대로 적용할 수 있다고 가정하지 않는다. 사용자가 확정한 요청을 서버가 수락하면 전환 원장과 포인트 차감을 원자 처리하고, 발급 실패·중복 처리는 감사 가능한 보정 원장으로 환원한다.
- 실제 온누리 상품권은 앱의 현재 충전·발급 조건과 발급 건별 만료일을 연동 계약/응답에서 확인해 기록한다. K&A가 임의의 공통 만료기간을 만들거나 과거 이벤트의 5년 조건을 모든 상품에 적용하지 않는다. K&A 포인트 자체는 로컬 프로토타입에서 만료·환수하지 않는다. 실서비스의 만료·환수 정책은 발행 상품 조건과 법무·회계 검토를 확인한 뒤 출시 조건으로 확정한다.
- 디지털 온누리 수동 충전은 최소 1,000원·1,000원 단위로만 가능하며 1,500원 같은 단위 불일치 금액은 불가하다. 2026-11-01 사용자가 디지털 온누리 챗봇에 문의해 전달한 답변을 확정 근거로 기록한다. K&A 전환 입력도 1P=1원에 맞춰 최소 1,000P·1,000P 단위로 제한한다. 소비자 계좌 충전과 실제 K&A 제휴 발급 조건은 구별한다.
- 인증이 필요한 callable Cloud Function은 `request.auth`가 없으면 명시적으로 거부한다. 토큰이 전달·검증되는 것만으로 함수 호출 권한이 자동 제한되는 것은 아니다. 대상 문서 권한과 클라이언트 입력도 다시 확인하고, 재시도에도 중복 지급되지 않도록 idempotency/트랜잭션을 설계한다.
- Functions의 Admin SDK는 Firestore Rules를 우회하므로, 규칙이 서버 코드의 검증을 대신한다고 가정하지 않는다.
- App Check는 앱/기기에서 온 요청인지 확인하는 추가 방어층이다. 사용자 신원·문서 권한을 판정하는 Firebase Auth나 Security Rules를 대신하지 않는다. 사용할 서비스가 지원되는지 확인하고, 모니터링 후 단계적으로 강제한다.
- App Check가 있어도 인증된 계정의 스팸이나 정상 클라이언트의 반복 호출이 자동으로 해결되지는 않는다. 질문·답변 등록 제한이나 비용이 드는 기능의 호출량 제어가 필요해지면 서버에서 별도로 설계한다.
- AI 공급자 키와 검색 관리자 키는 서버 비밀 저장소에 둔다. `VITE_` 변수는 공개 번들에 포함될 수 있으므로 비밀값을 넣지 않는다.
- AI 번역·분석은 Cloud Functions 등 서버 경유로 수행한다. 외부 AI에 보내는 본문은 기능에 필요한 최소량으로 제한하고, 민감 정보 제거·사용자 고지·공급자 보관 정책을 확인한다. 사용자가 요청하지 않은 외부 전송을 하지 않는다.
- 답변 평가는 현재 로컬 단계에서도 서버 evaluator를 통한다. 질문 제목·본문·답변 본문과 실제 검색 근거로 입력을 한정하고, 전송 고지·민감정보 최소화·공급자 보관 조건을 확인한다. 평가 결과에는 실제 모델 식별자·룰 버전·질문/답변 revision·평가 시각·출처를 기록한다. 자체 출처 인덱스나 파인튜닝 모델이 이미 있다고 가정하지 않는다.
- AI 출력은 신뢰된 사실로 간주하지 않는다. 특히 체류·법률·의료 안내를 생성한다면 최신 공식 출처를 확인해 함께 안내하고, 포인트 지급·채택·권한 결정은 모델 응답만으로 확정하지 않는다.
- Firebase 웹 설정과 Algolia Search-only 키는 브라우저에 노출될 수 있다. 이 공개 가능성은 데이터 접근 제어를 대체하지 않는다. 로컬 프로토타입에서는 Firebase·Algolia 네트워크 요청을 기본적으로 수행하지 않는다.
- 비로그인 검색을 막기 위해 클라이언트에 무제한 Search-only 키를 배포하지 않는다. MVP 검색은 인증된 Firestore 조회가 감당하는 범위에서 시작한다. Algolia가 필요해지면 인증을 확인하는 서버 프록시 또는 사용자별 제한·차단 필터가 포함된 secured API key를 발급한다. 인덱스에는 최소 필드만 동기화하고, 개인정보·첨부 URL·삭제된 질문을 넣지 않는다. Firestore Rules는 Algolia 검색을 보호하지 않는다.
- 개발/운영 Firebase 프로젝트는 분리하고 로컬 개발·보안 검증은 Emulator를 우선한다. 한국 사용자 대상 신규 Firestore·Functions는 `asia-northeast3`(서울)를 기본 후보로 삼고, Functions와 데이터 리소스를 같은/가까운 지역에 배치한다. Storage 버킷의 실제 가능 지역·가격·프로젝트 종속성을 생성 전에 확인한다. Firestore 위치는 생성 후 바꿀 수 없으므로 운영 DB 생성 전 검토한다.
- 프로토타입에서는 App Check와 실서비스 서버 권한을 구현된 것처럼 취급하지 않는다. Firebase 실서비스 공개 전에는 지원 서비스에서 App Check를 관찰 모드로 확인한 뒤 enforcement를 적용한다.

### 4.5 비밀값과 로컬 설정

- 저장소에 서비스 계정 키, Functions 비밀값, 실사용 비밀번호, 토큰 또는 관리자 키를 커밋하지 않는다. 7.1절에서 사용자가 지정한 이메일 식별자와 데모 비밀번호는 로컬 목업 인증 설정 및 이 하네스의 시연 정의로만 사용한다. 이 정의는 실제 Google 인증이나 외부 계정 접근 지시가 아니다. IndexedDB 프로필·로그·오류 메시지·LLM 입력에는 비밀번호를 저장하거나 남기지 않는다.
- 브라우저용 `VITE_*` 값은 비밀이 아니며, 공개되어도 안전한 값만 둔다.
- `.gitignore`는 모든 디렉터리의 `.env`와 `.env.*`를 제외하고 `.env.example`만 공유 가능한 템플릿으로 허용한다. `.env.example`에는 빈 값 또는 설명만 둔다. 현재 프론트 실행에는 환경 변수나 API 키가 필요하지 않으며, 향후 로컬 Node API의 키 로딩은 해당 단계에서 구현·검증한다. 자세한 실행 방법은 루트 `README.md`를 따른다.
- K&A는 체류·의료·고용 등 민감한 사연이 질문 본문에 포함될 수 있다. 주민등록번호·외국인등록번호, 여권/신분증 이미지, 계좌 정보, 정확한 주소·전화번호처럼 기능에 불필요한 정보를 요구하거나 공개 로그에 남기지 않는다. 질문 첨부는 일반 설명 이미지로 제한하고 신분증·여권·계좌 증빙 업로드를 요청하거나 유도하지 않는다.
- 로그와 오류 메시지에서 인증 토큰, 비밀번호, 개인정보, 질문의 민감한 내용을 불필요하게 남기지 않는다.

### 4.6 Firebase 선택 시 보안 규칙 변경 절차

이 절차는 Firebase 백엔드를 실제로 선택한 경우에만 적용한다. SQL 백엔드라면 마이그레이션과 RLS 검증에 맞는 별도 절차를 작성한다.

1. 컬렉션/스토리지 경로, 각 필드의 신뢰 주체, 공개 범위, 생성·수정·삭제 권한을 먼저 문서화한다.
2. Firestore와 Storage Rules는 기본 거부로 작성한다. 정책 변경에는 허용 사례와 거부 사례를 모두 포함한다.
3. Emulator는 저장소에 연결된 규칙 파일을 실제로 읽는지 확인한다. 규칙 파일/경로 설정이 빠진 Emulator는 열린 접근으로 동작할 수 있으므로, "Emulator에서 실행했다"만으로 보안 검증을 통과했다고 하지 않는다.
4. 가능하면 실제 Firebase 리소스가 없는 `demo-` 프로젝트 ID를 사용하고, Emulator 연결이 확인되지 않으면 테스트 데이터를 입력하지 않는다. Emulator가 실행 중이지 않거나 일부 서비스만 에뮬레이션되는 경우 요청이 실제 Firebase로 갈 수 있음을 확인한다.
5. 웹 앱에서 인증·Firestore·Storage를 점검할 때 `VITE_USE_EMULATOR=true`와 각 연결 주소를 확인한다. 환경 변수 설정만으로 Emulator 연결이 검증된 것은 아니다.
6. Firebase Emulator Suite와 Rules Unit Testing으로 비로그인, 본인, 다른 사용자, 잘못된 필드·값을 검증한다. 운영자 모델이 없는 프로토타입에 운영자 예외를 만들지 않는다.
7. Emulator에서 확인한 규칙만 배포 대상으로 삼고, 실제 Firebase 프로젝트 반영은 사용자 요청 없이 실행하지 않는다.
8. Rules가 데이터 유효성 검사와 서버 비즈니스 로직을 모두 대신한다고 가정하지 않는다.

### 4.7 현재 개발 범위: 제한된 외부 LLM 책정·평가

- 앱 데이터는 IndexedDB에 두고 질문 책정·답변 평가 요청은 로컬 Node API를 경유한다. API 키는 서버 환경 변수에만 두며 브라우저 번들·`VITE_*`·IndexedDB에 넣지 않는다. Node API는 loopback으로 제한하고 origin·입력 크기·빈도를 검사한다. 데모 로그인을 실서비스 API 인증으로 간주하지 않는다.
- 질문 책정의 외부 입력은 질문 제목·본문과 정책 버전·설명 언어로 제한한다. 답변 평가는 질문 제목·본문·답변 본문, 평가 제어 정보, 실제 검색 근거를 사용한다. 계정 자격 증명·프로필·첨부·잔액을 보내지 않는다. 질문 책정의 긴급 여부와 금액 계산은 앱에서 처리한다. 두 기능의 전송 범위를 안내하고 허구 시연 원고를 사용하며 요청 본문을 로그에 남기지 않는다.
- 답변 평가에 필요한 일반 웹 검색과 구조화 출력의 동시 지원은 선택한 모델·API·추론 설정으로 연결 시 확인한다. 기능별 지원 목록만으로 한 요청의 조합까지 검증됐다고 가정하지 않는다. 미지원 조합이면 확보한 검색 근거로 두 번째 요청에서 판정·구조화하며, 판정 지시는 한 요청·두 요청 모두에 포함한다. 두 번째 요청에서 새 검색은 하지 않는다.
- 첫 구현의 시도별 제한은 아래 표를 따른다. 두 기능은 전체 동시 실행 1개의 공통 대기열을 사용하지만 작업 종류·중복 요청 키·상태·저장 결과는 분리한다. 같은 종류·같은 대상의 중복 요청만 합친다. 대기열 대기부터 해당 시도의 모든 요청 완료까지 하나의 제한 시간을 적용하며, SDK를 포함한 자동 재시도는 0회다. 시간 초과·취소된 대기 작업은 제거하고, 이미 실행한 작업의 늦은 응답은 저장하지 않는다.

| 작업 종류·기준 | 모델 요청/시도 | 검색/시도 | 전체 제한 시간 | 실패 후 동작 |
|---|---:|---:|---:|---|
| `question_reward` · `kna-reward-v1` | 1회 | 0회 | 대기열 포함 20초 | 재시도 또는 사용자가 기본 보상 등록 선택 |
| `answer_evaluation` · `kna-evidence-v1` | 최대 2회 | 최대 3회·최종 출처 최대 5개 | 대기열·두 요청 합계 45초 | 총점 없이 사유 표시, 사용자 재시도 가능 |

- 도구 횟수·입력 크기·출력 토큰·빈도 제한은 실제 공급자/서버 기능으로 집행한다. 표의 시간·호출 제한은 연결 시 확인할 운영 설정이며, 미완료 응답을 성공으로 처리하지 않는다. 정기 수집·심층 검색·자동 무한 재시도는 하지 않는다. 세부 계약은 두 확정 룰을 따른다.
- API 키 미설정·오프라인·사용량 제한·시간 초과·검색 실패·형식 오류에는 실패 상태를 표시한다. 답변 평가는 임의 점수를 만들지 않으며 기존 수동 채택은 가능하다. 질문 책정 실패·판정 보류에는 원고를 유지하고 재시도 또는 사용자가 선택하는 기본 보상 등록(일반 100P·긴급 150P)을 제공한다. 기본 보상을 AI 책정으로 표시하지 않는다. 외부 API·검색 이용료가 발생할 수 있으므로 무료 ChatGPT 사용권과 동일하게 취급하지 않는다.
- 답변 평가는 실제 검색 실행과 근거 URL을 확인하고 모델 출력을 구조 검사한다. 질문 책정 모델은 허용 등급만 제안하고 Node API와 앱이 이를 검사해 정책 금액을 계산한다. 모델은 출처·날짜를 꾸미거나 금액·가산율·채택·지급·권한을 직접 만들거나 변경할 수 없다. 사용자 글과 검색 페이지의 지시는 책정·평가 규칙으로 실행하지 않는다.
- 첫 구현은 확정된 두 룰을 각각 프롬프트와 출력 검사에 적용한다. 실제 가중치 파인튜닝은 현재 개발 범위에 포함하지 않으며, 답변 평가 문서 8절은 향후 별도 도입 시의 라벨링 기준이다. 룰 확정을 학습 데이터 업로드나 모델 학습 실행 지시로 해석하지 않는다.
- 판정 기준·출력 의미가 바뀌면 `rubricVersion`, 보상 등급·금액·가산 정책이 바뀌면 `rewardPolicyVersion`을 올리고 부속 문서와 하네스를 함께 갱신한다. 기존 답변 결과를 새 기준으로 바꿔 표시하거나 기존 질문의 확정 보상·지급 원장을 새 금액표로 덮어쓰지 않는다.

## 5. 프론트엔드 보안·품질

- 사용자 입력은 React 기본 텍스트 렌더링을 사용한다. `dangerouslySetInnerHTML`은 사용하지 않는다. 꼭 필요하면 먼저 요구 사유를 확인하고 안전한 정화 방식을 설계한다.
- 로컬 프로토타입의 라우트 가드와 데모 로그인은 화면 흐름만 제어하며 보안 경계가 아니다. 향후 서버 연결 시 접근 제어는 선택한 백엔드에서 강제한다.
- 비밀번호를 Zustand persist, IndexedDB, `localStorage`, URL, 로그에 저장하지 않는다. 실제 인증을 선택하면 해당 인증 공급자가 세션을 관리하게 한다. 로컬 데모 자격 증명은 가짜 값이며 번들에서 확인할 수 있다.
- 서버 응답과 폼 입력은 화면의 편의 검증과 별개로 보안 경계에서 검증한다.
- UI는 현재 프로젝트의 React Router, Zustand, i18next, CSS/Tailwind 구성을 존중하고, 새 라이브러리는 필요한 경우에만 추가한다.
- 새 UI 문구는 기존 i18next 리소스(`src/i18n/locales`)에 추가하고, 화면에 임의의 한국어 문자열을 하드코딩하지 않는다. 기계 번역은 사용자가 작성한 원문을 덮어쓰지 않고 원문과 번역문을 구분한다.
- 한국어가 익숙하지 않은 사용자를 위해 입력에는 접근 가능한 이름과 오류 안내를 제공하고, 버튼/링크의 의미 있는 이름·키보드 포커스·충분한 대비·작은 모바일 화면을 함께 고려한다.

## 6. 보안 작업 시 완료 조건

보안 규칙·Functions·Firebase 데이터 흐름을 변경하는 작업은 해당 범위에 맞는 아래 내용을 완료 보고에 포함한다.

- 영향을 받는 경로와 허용/거부 주체
- 서버에서만 가능한 필드와 연산
- 실행한 Emulator/Rules 검증 명령 및 결과. 실행하지 못했다면 그 이유
- 규칙만으로 막을 수 없는 서버 코드 또는 운영 설정의 남은 조건

기능 화면만 바뀐 작업에는 보안 검증 절차를 무조건 확대 적용하지 않는다.

## 7. K&A 제품 정책 기준선

이 항목은 현재 요청에서 확정한 정책과 1인 프로토타입을 위한 기본 결정을 모은다. 현재는 로컬 저장소 구현도 시작 전이며, 아래는 제품 기준이다. Firebase Rules·Functions 또는 다른 서버 정책으로 적용된 상태가 아니다. 개발 전 모든 실서비스의 금전·운영 조건을 확정해야 한다는 뜻은 아니다. 로컬 프로토타입, 서버 동기화, 대외 공개 시점의 선행 조건을 7.7에서 분리한다.

### 7.1 로그인과 프로필

- 비로그인 사용자는 로그인·정책 안내 화면만 이용할 수 있다. 첫 로컬 시연에는 가입 기능을 넣지 않고 두 개의 준비된 데모 계정만 제공한다. 질문·답변·첨부·검색 데이터는 로그인 후에만 연다.
- 모든 인증 사용자는 질문과 답변을 열람할 수 있다. 작성 시 본인 UID로 귀속한다. 다른 사용자의 공개 프로필에는 닉네임, 선택형 아바타, 국가 같은 최소 정보만 둔다. 닉네임은 영문 ASCII 알파벳·숫자와 단어 사이 공백을 허용하고, 한글·한자·베트남어 발음기호 등 다른 문자와 기호는 허용하지 않는다. 사용자가 지정한 `cutetl123`을 수용하기 위해 이전의 숫자 금지를 해제했다. 닉네임 끝의 `!`는 포함하지 않는 것으로 사용자가 확인했다. 이메일·전화번호·실명·정확한 주소는 공개 프로필에서 제외한다.
- 프로토타입은 아래 두 가짜 계정만 허용하는 로컬 데모 로그인을 제공하고, 로그인한 계정의 프로필과 소유 데이터를 IndexedDB에서 불러온다. 이메일과 비밀번호를 문자 단위로 정확히 비교하며 하나라도 틀리면 로그인하지 않는다. 인증 실패 문구는 `이메일 또는 비밀번호가 올바르지 않습니다.`로 통일해 계정 존재 여부를 노출하지 않는다.
- 로그아웃·로그인 화면은 브라우저 기본 언어를 따른다. 로그인 성공 후에는 계정의 `uiLanguage`가 우선하며, 질문자 계정은 중국어 간체(`zh-CN`), 답변자 계정은 베트남어(`vi`)로 고정한다. 따라서 영어 설정의 맥북에서도 질문자는 중국어, 답변자는 베트남어 UI를 본다. 계정 언어가 없거나 지원 목록 밖이면 브라우저 기본 언어를 적용한다. 지원 브라우저 언어는 한국어·영어·베트남어·중국어이며, 나머지 언어 설정은 영어로 대체한다.

| 시연 역할 | 닉네임 (영문·숫자) | 시연 배경 | 로그인 후 UI 언어 | 이메일 식별자 | 데모 비밀번호 | 시작 포인트 |
|---|---|---|---|---|---|---|
| 질문자 | `skyking` | 중국 국적, 한국 거주 | `zh-CN` | `skyhao@gmail.com` | `skyhao2195!` | 1,000P |
| 답변자 | `cutetl123` | 베트남 국적, 한국 거주 | `vi` | `thilinh@gmail.com` | `thilinh7692!` | 1,000P + 과거 표시 스냅샷 |

- 계정 식별자·비밀번호·닉네임은 사용자가 로컬 시연용으로 지정한 값이다. 입력을 정확히 비교하고 자동으로 다른 이메일 도메인으로 고치지 않는다. 실제 Google 계정의 존재·소유권을 확인한 것이 아니며 이메일 발송·외부 로그인에 사용하지 않는다. 비밀번호는 로컬 인증 검사용 설정에서만 다루고 사용자 프로필·IndexedDB·로그·외부 LLM 입력에 넣지 않는다. 성별·체류 자격·구체적인 거주지 등 추가 개인정보를 만들지 않는다. 로컬 데모 인증은 실서비스 보안 경계가 아니다.

### 7.2 질문·답변과 채택

- 질문 작성자는 본인 질문을 언제든 편집·삭제한다. 삭제는 화면과 검색에서 즉시 제거하고 첨부 파일을 지운다. 회계·채택 정합성을 위한 최소 이벤트와 원장은 유지한다.
- 답변 작성자는 본인 답변을 언제든 편집한다. 미채택 답변은 삭제할 수 있다. 채택 답변은 삭제할 수 없고 편집은 허용한다. 답변 수정은 채택 사실이나 이미 지급된 포인트를 바꾸지 않는다.
- 질문자는 수동 채택을 우선 권장받고, 답변 선택 후 채택 버튼을 누르면 `이 답변을 채택할까요?` 확인 모달을 연다. 모달에서 `채택하기`를 선택한 경우에만 즉시 확정하며 `취소`는 모달만 닫고 채택·포인트 상태를 바꾸지 않는다. 모달의 수령자 닉네임과 지급 포인트는 실제 선택 답변과 질문 등록 시 확정 보상에서 읽고, Figma의 `…님에게 …P가 지급되고, 채택 후에는 바꿀 수 없어요.` 표현을 따른다. 질문자가 질문 등록 후 7일 안에 직접 채택하지 않으면 보완 정책으로 아래 유효 평가 후보 중 가장 높은 참고 점수의 답변을 자동 채택한다. 질문당 한 답변만 채택할 수 있고, 수동·자동 채택 모두 확정 후에는 취소할 수 없다. 로컬 프로토타입은 이 상태와 목업 보상만 반영한다. 실서비스에서는 서버가 기한·평가 완료 상태·질문/답변 관계를 확인하고 중복 없이 처리한다.
- 답변 점수는 질문자에게만 표시하며, 화면의 점수 배지와 `AI 신뢰도` 관련 문구는 승인된 현재 Figma를 유지한다. `AI 참고 점수`라는 별도 명칭을 점수 옆에 강제로 추가하지 않는다. [평가 룰](./ANSWER_EVALUATION_RULES.md)의 핵심 사실별 근거 일치 판정을 평균하고 소수점 한 자리로 표시하며, 이유·실제 출처·평가 시각은 결과 상세에서 확인할 수 있게 제공한다. 문서 내부의 참고 점수라는 표현은 제한된 검색 비교라는 의미이며 고정 UI 명칭이 아니다. 이는 정답일 확률이나 정확성 보장이 아니다. 문체·친절도 등 품질 채점은 제외한다. 수동 채택을 강제하거나 다른 포인트·신고·제재·검색 순위를 바꾸지 않으며, 7일 미채택 때만 자동 채택 비교값으로 사용한다.
- `llm` 모드를 명시적으로 활성화하고 전송 안내를 제공한 뒤 답변 저장·관련 질문 제목/본문 수정 시 평가를 예약한다. 같은 질문/답변 revision·룰 버전 결과는 저장해 재사용하고 재렌더·새로고침·재로그인으로 호출하지 않는다. 질문 제목/본문이나 답변 본문 수정 시 기존 평가를 무효화하며, 이전 요청의 늦은 응답으로 최신 결과를 덮어쓰지 않는다. UI 언어·포인트·채택 상태 변경만으로 재평가하지 않는다.
- 7일 자동 채택은 현재 revision·동일 룰 버전의 `completed`인 llm 평가 후보만 비교한다. 보류·실패·처리 중·stale·mock 및 삭제 답변은 제외한다. 동점이면 먼저 등록된 답변, 등록 시각도 같으면 답변 ID 오름차순으로 선택한다. 후보가 없으면 미채택으로 유지하고 이후 유효 결과가 생기면 다시 확인한다. 로컬 앱 시작/복귀·활성 화면의 기한 도달·유효 평가 저장 시 처리하며 앱 종료 중 실행을 보장하지 않는다. 기한은 질문 생성 시각 + 7일이고 수정으로 연장하지 않는다. 확정 직전 상태를 재검사하고 채택·목업 보상을 한 트랜잭션으로 처리한다.
- 점수 열람은 해당 질문의 작성자에게만 허용한다. 답변 작성자나 다른 계정에게는 표시하지 않는다. IndexedDB 단계의 조건 검사는 시연 UI일 뿐 보안 경계가 아니며, 향후 서버 평가 결과는 서버가 질문 작성자 권한을 확인한 뒤 제공한다.
- 근거 부족·검색 실패·출처 충돌·질문 조건 부족은 총점 없이 이유를 표시한다. 0점은 확인된 모순을 뜻하므로 실패 상태에 사용하지 않는다. 질문과 무관하거나 확인 가능한 사실이 없는 답변도 채점하지 않는다. 오프라인 시연에 별도 mock 모드를 선택할 수 있지만 `시연용 점수 · AI 평가 아님`을 표시하고 llm 결과와 저장·비교를 분리한다. 실제 LLM 실패 때 mock으로 자동 전환하지 않는다. 파인튜닝용 라벨 기준은 부속 문서에 두되 현재 모델 학습을 수행하거나 정확도가 검증됐다고 표현하지 않는다.
- 질문 삭제는 채택 취소로 처리하지 않는다. 이미 발생한 포인트 원장은 유지한다. 로컬 시연 보상은 7.5절의 질문 등록 시 확정한 보상 스냅샷을 사용하고, 수동 또는 7일 후 자동 채택이 확정됐을 때 답변자의 목업 잔액·원장에 한 번 반영한다. 1P=1원 환산율과 긴급 시 기본액에 50% 가산은 사용자 확정 사항이며, 보상 금액 후보는 프로토타입 v1 확정값이며 실서비스 보상·재원 정책과 구분한다.

### 7.3 신고·차단·URL 공유

- 질문 상세 우측 상단 `⋮` 메뉴 항목과 순서는 `신고`, `차단`, `URL 공유`로 고정한다. 사용자 본인 게시글에는 신고·차단을 노출하지 않는다.
- 신고는 사유 하나를 고르게 한다: `욕설/비하`, `상업적 광고 및 판매`, `유출/사기/사칭`, `낚시/도배`, `불법촬영물 등이 유통`. 로컬 프로토타입은 선택 UI와 로컬 확인 표시까지만 제공하고, 외부 신고 전송·운영자 계정·관리자 콘솔·심사 처리는 구현하지 않는다.
- 차단은 확인 모달 없이 즉시 해당 질문을 현재 사용자 화면의 목록·검색·상세에서 제외한다. 질문 단위·사용자 개인 설정이며 작성자의 다른 게시글은 차단하지 않는다. 설정의 차단 목록에서 해제할 수 있다. 별도의 일반 숨김 기능은 만들지 않는다.
- `URL 공유`를 선택하면 `클립보드에 복사되었습니다`라는 토스트/작은 모달을 약 2초간 표시하고 사라지게 한다. 이는 시각적 목업 전용이다. URL을 생성하지 않고 `navigator.clipboard`, Web Share API, 실제 복사·공유를 호출하지 않는다.
- 로컬 프로토타입은 차단 상태와 신고 선택을 데모 사용자 ID별 IndexedDB 데이터로 저장한다. 게시글·답변·설정 등 시연용 가짜 데이터도 저장할 수 있으나 실제 개인정보나 민감정보는 넣지 않는다.
- 운영자 권한은 로컬 프로토타입에서 제외한다. 공개 실서비스 전에는 신고 확인·불법촬영물 등 긴급 신고 대응·콘텐츠 삭제·이의제기 책임자를 정하고 필요한 서버 권한을 별도 설계해야 한다. 그 전까지 공개 배포를 승인된 상태로 보지 않는다.

### 7.4 첨부

- 상품권 만료일은 각 발급 건에서 확인된 실제 발행 조건의 날짜를 그대로 저장·표시한다. 공통 만료일을 임의로 설정하지 않는다. 공식 상품 약관은 유효기간을 상품별로 정할 수 있다고 안내하므로, 제휴 개발 전 최신 발행 조건과 환불·소멸 규정을 다시 확인한다.
- 환산율 1P=1원은 확정되어 있다. 프로토타입의 보상 등급·금액·긴급 가산은 v1로 확정했다. 실서비스 보상 수치·재원과 제휴를 통한 실제 발급 조건은 실제 포인트·전환 서버 기능을 만들기 전에 별도로 확정한다. 로컬 프로토타입의 전환은 안내 토스트까지이며 차감과 전환 기록은 실제 연동 단계에서 구현한다.

### 7.6 검색·AI·클라우드 운영

- 로컬 단계의 검색은 IndexedDB에서 현재 사용자가 볼 수 있는 질문을 대상으로 수행한다. Algolia 도입 시 Firestore Rules가 Algolia를 보호한다고 가정하지 않고, 서버 프록시 또는 사용자별 제한 키를 설계한다. 차단·삭제된 질문은 검색에서 제외한다.
- 현재 외부 LLM 호출은 두 경로로 제한한다. 질문 보상 책정은 전송 안내·명시적 llm 모드에서 유효한 질문의 등록 버튼을 눌렀을 때만 실행하고, 타이핑·화면 진입으로 호출하지 않는다. 답변 평가는 4.7절과 7.2절의 답변 저장·관련 질문 제목/본문 수정 이벤트에 따라 별도로 실행하며, 답변이 없는 새 질문 등록만으로 답변 평가를 호출하지 않는다. 번역 등 다른 AI 기능은 별도 도입 범위로 두고 비밀 키는 서버에 둔다.
- 향후 Firebase 운영 자원을 선택할 경우 한국 사용자에게 적합한 리전과 가격을 확인하고 개발·운영 프로젝트를 분리한다. Firestore 위치는 생성 전에 결정한다.
- App Check는 Firebase 실서비스 공개 전 단계적으로 도입한다. 인증·Rules·서버 권한과 별개인 추가 방어층으로 취급한다.

### 7.7 단계별 결정과 출시 전제

- **현재 로컬 프로토타입 단계:** 가짜 데모 계정·프로필·사용자가 작성하는 질문·답변·설정·차단·신고 선택·포인트 이력과 질문/답변 revision별 평가 결과를 IndexedDB에 저장한다. 두 계정 각각 초기 1,000P와 답변자 전용 과거 표시 스냅샷, 1P=1원 표시, 새 전환 시도 시 잔액 변경 없는 안내 토스트를 제공하며 시드와 초기화 절차로 상태를 재현한다. 전환 시도로 원장이나 전환 내역을 추가하지 않는다. 비동기 저장소 모듈을 사용해 이후 데이터 서버 adapter로 교체하기 쉽게 하되, 온라인 로그인·Firebase/Supabase 연결·다중 기기 동기화는 구현하지 않는다. 외부 호출은 로컬 Node API를 통한 검색 없는 질문 보상 등급 분류와 제한된 웹 검색 기반 답변 평가만 추가한다. 질문 등록 시 확정 보상과 책정 출처도 저장한다. 실제 상품권 발급·신고 서버 전송·자체 RAG 자료 수집·모델 학습 작업은 현재 구현에 포함하지 않는다. LLM 평가는 인터넷이 필요하지만 데이터 저장·기본 화면은 로컬에서 동작한다.
- **첫 시연 우선순위:** 1) 로그인(중국인 질문자·베트남인 답변자 데모 계정), 2) 홈, 3) 게시판, 4) 질문글 작성(제한된 포인트 책정·실패 시 기본 보상 등록 포함), 5) 포인트 페이지 순으로 완성도와 시연 안정성을 우선한다. 질문 상세, 답변 작성·수정, 질문자 전용 답변 평가 점수와 7일 미채택 자동 채택은 두 계정 간 질문/답변 흐름을 설명하는 보조 시연 경로로 지원한다. AI 결과의 화면 문구는 승인된 Figma를 따르되 실제 평가 범위는 제한된 검색 비교를 유지하고, 채택과 포인트는 로컬 목업 상태만 갱신한다. 사용자가 시연용 질문·답변 원고를 별도로 준비해 직접 붙여 넣으므로, 질문·답변 원문은 앱에 시드하지 않는다. 반복 가능한 시드에는 두 계정·프로필과 목업 포인트 등 계정 및 시연 준비 데이터만 둔다.
- **다국어 UI와 화면 검수:** 로그아웃·로그인 화면은 브라우저 언어, 로그인 후에는 해당 데모 계정의 `uiLanguage`를 사용한다. 우선순위 화면 및 시연 경로에 필요한 메뉴·모달·오류 문구는 한국어·영어·베트남어·중국어 간체 리소스를 제공한다. 글꼴 대체, 베트남어 발음기호, CJK 글리프, 버튼/카드 폭, 줄바꿈, 잘림과 세로 길이를 네 언어에서 확인한다. 언어마다 별도 화면을 다시 디자인하지 않고 유연한 레이아웃으로 수용한다.
- **로컬 데이터 구조:** 계정과 콘텐츠는 안정적인 ID 및 `ownerId`로 연결하고 생성·수정 시각은 UTC로 기록한다. 포인트는 원장 항목과 시연용 잔액을 구분한다. 동기화 충돌·삭제 전파·서버 권한을 로컬 단계에서 가정해 구현하지 않는다.
- **서버 동기화 설계 전:** 백엔드 공급자와 API 계약, 데이터 이전, 인증 세션, 개인정보 보관, 동기화 충돌·삭제 정책을 결정한다. 필요한 정책만 확정하고 Firebase·SQL 중 하나를 지금 전제하지 않는다.
- **포인트/상품권 서버 기능 개발 전:** 사용자 확정 환산율 1P=1원을 기준으로 답변 채택 보상액과 지급 재원, 운영 최소 전환액·단위, 월/계정별 한도, 오류·부정 이용 보정, 거래 취소/환불 처리를 정한다. 정책에는 버전 ID를 두고 서버가 적용 시점의 정책을 기록한다. 로컬 목업의 보상 등급표를 실서비스 정책으로 그대로 재사용하지 않는다. AI의 등급 제안과 정책 금액·긴급 50% 가산·지급 권한을 분리하고 신뢰 서버가 최종 검증·계산한다.
- **온누리 연동 전:** 발행 사업자와 제휴 가능 여부, 공식 API/앱 핸드오프, 앱 설치·미설치 분기, 본인 확인, 발급 성공/실패 응답, 발급 건별 유효기간·환불 조건을 확인한다. 공개된 소비자 안내만으로 제3자 발급 연동이 가능하다고 간주하지 않는다. 조건이 확보되지 않으면 전환 기능은 잔액 차감·내역 저장 없이 안내 토스트만 제공하는 목업으로 유지한다.
- **공개 배포 전:** 신고를 실제로 접수·검토할 운영 책임자, 처리·긴급 대응·삭제·이의제기 절차, 개인정보 고지·보유기간을 정하고 구현한다. 신고가 실제 접수되지 않는 목업 상태로는 공개 서비스에 배포하지 않는다. 온누리 제휴가 성립하지 않으면 실제 전환을 제거하거나 미지원 상태를 명확히 안내한다.
- 따라서 목표 명칭은 **로컬 데이터 기반의 서버 동기화 준비형 프로토타입**으로 둔다. 로컬 데이터는 현재 PC·브라우저에만 저장되며 다른 PC에서 공유되지 않는다. 서버 어댑터를 추가하는 것만으로 공개 배포가 끝난다고 표현하지 않는다.

## 9. K&A 데이터 모델 출발안

아래 항목은 로컬 프로토타입과 향후 서버 모델 설계를 위한 **도메인 엔터티 제안**이며, 현재 저장소의 구현이나 확정 스키마가 아니다. Firebase 경로에 종속하지 않는다. 실제 개발에서는 각 화면의 요구와 조회 패턴을 확인한 뒤 필드와 관계를 확정한다.

| 제안 엔터티 | 포함할 데이터와 권한 경계 |
|---|---|
| 데모 계정·프로필 | 안정적인 사용자 ID, 사용자 지정 이메일 식별자, 영문·숫자 닉네임, 국가, 계정별 `uiLanguage`, 개인 설정. 로그인 후에는 지원되는 `uiLanguage`가 브라우저 기본 언어보다 우선한다. 이메일은 공개 프로필과 분리하고 비밀번호는 프로필·DB에 저장하지 않는다. |
| 질문 | 안정적인 질문 ID, 작성자 ID, 제목·본문·revision, 카테고리·긴급도, 생성·수정 시각, 삭제·채택 상태. 등록 시 확정 보상 스냅샷과 책정 출처를 함께 보관한다. |

| 답변 | 안정적인 답변 ID, 질문 ID, 작성자 ID, 본문, revision, 생성·수정 시각, 채택 상태. |
| 답변 평가 | 질문·답변 ID와 각각의 revision, 질문 작성자 ID, 평가 상태, 완료 시 0.0~100.0 점수 또는 null, 평가 유형(`llm`/명시적으로 선택한 `mock`), 기준·모델·출처 버전, 평가 시각. 질문 작성자만 조회하며 질문 제목/본문 또는 답변 수정 시 이전 평가를 무효화한다. 질문 보상 책정과 별도 결과이며 아직 구현 전 설계다. |
| 사용자 설정·차단·신고 목업 | 소유자 ID를 기준으로 한 개인별 설정, 차단 목록, 신고 선택 상태. 다른 사용자의 데이터에 영향을 주지 않는다. |
| 포인트 원장 | 계정 소유자 ID, 고유 항목/요청 ID, 정수 포인트 증감량, 종류(`demo_opening`·채택 보상), 연결된 질문·답변 ID, 채택 시 확정 보상액·보상 정책 버전·책정 출처, 생성 시각, 목업 구분. 시작 원장은 질문자·답변자 각각 +1,000P를 한 번 기록한다. 로컬 전환 시도는 원장 항목을 생성하지 않는다. 원장은 추가 방식으로 기록하고 화면 잔액은 합산 결과 또는 일치하는 캐시로 표시한다. |
| 과거 포인트 표시 스냅샷 | 답변자 소유자 ID, 시드 버전·기준 시각/월, 7.5절의 4개 표시 내역과 월간 +400P·3회 요약. `demo_history` 출처로 실제/신규 거래와 구분한다. 잔액을 바꾸지 않고 초기 원장에 중복 반영하지 않는다. 기존 글·답변을 만들거나 실제 발급 ID를 부여하지 않는다. |
| 첨부 메타데이터 | 질문 ID, 로컬 파일 ID, 형식·크기·생성 시각. 로컬 Blob 또는 샘플 자산을 사용하며 실제 클라우드 URL은 저장하지 않는다. |
| 향후 상품권 전환 | 현재 새 전환 시도는 안내 토스트만 표시하고 요청/발급 데이터를 저장하지 않는다. 답변자의 사전 -2,000P 내역은 표시용 시연 스냅샷이다. 실제 서버·상품권 연동 단계에서 전환/요청 ID, 계정 소유자 ID, 전환 포인트, 1P=1원 환산율, 원장 연결과 발급 상태를 설계한다. |

- IndexedDB의 엔터티는 사용자 ID로 구분하고, 로그인·로그아웃·계정 전환 시 현재 화면 데이터가 올바른 사용자 기준으로 다시 읽히게 한다.
- 화면에서 표시하는 포인트와 Zustand 상태는 캐시/표시용이다. 로그아웃이나 계정 전환 때 다른 사용자의 캐시가 보이지 않도록 한다.
- 로컬 시드 계정은 테스트 전용이다. 사용자 지정 이메일 식별자는 비공개 계정 데이터로 저장하고, 비밀번호는 시드 DB·사용자 프로필·로그에 저장하지 않는다. 추가 실제 개인정보를 수집하지 않는다.
- 이 도메인 모델을 Firebase Rules나 SQL 스키마에 그대로 복사하지 않는다. 서버 공급자를 정한 뒤 접근 제어와 물리 스키마를 별도로 설계한다.

## 10. 1인 개발과 Git 작업 방식

- 프론트엔드와 백엔드를 별도 브랜치로 나누지 않는다. 한 기능은 화면·데이터·보안 경계를 함께 고려해 작은 단위로 완성한다.
- 기본은 현재 브랜치에서 작업하고, 작고 되돌리기 쉬운 변경을 한 번에 하나씩 진행한다. 큰 기능을 격리해야 하거나 사용자가 요청하면 짧은 작업 브랜치를 만든다. 새 브랜치 이름은 `codex/<짧은-작업명>` 형식을 쓴다.
- 작업 전 `git status`와 현재 브랜치를 확인하고, 이미 존재하는 변경은 보존한다. 요청 없이 `reset`, `clean`, 강제 checkout 등 사용자의 작업을 버릴 수 있는 명령을 실행하지 않는다.
- 커밋, 원격 push, PR 생성, merge는 사용자가 요청한 경우에만 수행한다. 브랜치 생성도 별도 요청 또는 작업 격리가 필요한 경우에 한한다.
- 브랜치가 이미 `main`이라고 해서 장기간 기능 브랜치를 만들거나 frontend/backend 브랜치로 쪼개지 않는다. 현재 상태에 맞춰 단순한 흐름을 유지한다.

## 11. Figma와 기존 프로토타입 참고

## 12. 작업 규모에 맞는 검증

- 작은 문구·정적 UI 변경에 과도한 테스트 인프라나 새 의존성을 추가하지 않는다.
- 변경한 코드 경로에 맞는 기존 명령을 선택한다. 프론트엔드 변경은 필요에 따라 `npm run lint`와 `npm run build`를 사용하며, 실행하지 않은 검증을 통과했다고 보고하지 않는다.
- 답변 평가·채택 UI를 바꾸면 질문 작성자·답변 작성자·다른 계정의 표시 권한, revision 변경 시 사실 평가 무효화·재평가와 확정 보상 유지, 새로고침 후 값 유지, 7일 자동 채택의 유효 최고 점수 선택 및 저장된 보상액의 중복 지급 방지를 확인한다. 명시적 mock 모드에서 외부 네트워크 호출이 없고 LLM 실패를 목업 점수로 바꾸지 않는지 확인한다. 승인된 Figma 문구를 유지하면서도 실제 점수·처리 상태와 근거 상세가 저장된 평가 결과를 따르는지 확인한다.
- 질문 포인트 책정은 [책정 룰 7절](./QUESTION_REWARD_RULES.md#7-구현-시-확인할-사례)의 등급별 매핑·긴급 50% 가산 한 번·형식 오류·실패 시 명시적 기본 보상 선택 및 동일한 로그인·원고 검증·늦은 응답 폐기·중복 등록 방지·계정 전환·등록 후 보상 고정을 확인한다. 모델 입력에는 긴급 여부·계정·잔액·답변·첨부를 보내지 않고 검색 도구를 제공하지 않는지 확인한다. 공통 대기열에서 두 작업의 결과가 섞이지 않고, 각 작업의 대기 시간을 포함한 제한·자동 재시도 금지·취소 후 실행 방지가 적용되는지도 확인한다.
- 데모 로그인은 사용자 지정 이메일·비밀번호를 한 글자라도 바꾸면 거부하는지 확인하고, `skyking`·`cutetl123` 닉네임 및 계정별 언어가 올바르게 표시되는지 확인한다. 첨부는 20개·각 10 MiB·합계 50 MiB 이내 허용, 21개·개별/합계 한도 초과·허용하지 않은 형식 거부를 확인한다.
- 포인트·전환을 구현할 때 직접 입력의 빈칸·0·음수·소수·문자·최소액 미달·단위 불일치·잔액 초과 거부와 1,000P·5,000P·6,000P의 잔액 이내 허용, 전환 직전 잔액 재검사를 확인한다. 질문자·답변자 각각 1,000P 시작 잔액, 답변자만 과거 표시 스냅샷 노출 및 원장 이중 반영 방지, 1P=1원 표시, 유효 입력에서만 안내 토스트 표시, 전환 전후 잔액·원장 불변 및 신규 전환 내역 미생성, 반복 클릭·취소·새로고침·재로그인 후 잔액 불변, 초기화 시 계정별 시작 잔액·과거 스냅샷 복원을 확인한다. 답변자 1,000P에서 150P가 새로 채택되면 잔액 1,150P·새 내역 1개가 되고, 반복 조회로 재지급되지 않는지도 확인한다. 큰 금액의 검증은 별도 시험 데이터로 수행하고 기본 데모 잔액을 임의로 올리지 않는다.
- Firebase Rules를 실제로 도입하거나 바꾸는 작업은 허용과 거부 사례를 Emulator에서 확인할 수 있는 구성을 함께 마련한다. 프로젝트에 Rules 테스트가 없으므로 도입 시점에만 필요한 도구와 스크립트를 추가하고, Rules 경로가 정해지기 전에 테스트 인프라를 선행 구축하지 않는다.
- 보안 규칙을 실제 Firebase 프로젝트에 반영하는 일은 검증과 별개의 배포 작업이다. 사용자 지시 없이 수행하지 않는다.
